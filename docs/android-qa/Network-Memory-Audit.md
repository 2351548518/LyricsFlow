# 网络取消与歌词缓存检查

日期：2026-11-02。基于 v1.0.4 发布后的代码检查；本轮修改未发布新版本。

## 检查范围

审阅播放监听及封面重试、通用音乐接口、LRCLIB／AMLL 缓存、歌词时间轴与渐变、悬浮窗生命周期、逐曲选择、备份恢复和 GitHub 同步等关键路径。保留现有界面、主题色、歌词排布和动画实现。

## 已确认并处理

1. **切歌取消后，通用音乐接口仍可能继续阻塞读取。** 原先 `MusicApi.request` 在 IO 协程里直接调用阻塞 HTTP 读取，协程取消不能及时释放等待者，旧请求还可能继续读取、解析和写入缓存。抽出 `MusicHttp`：使用共享固定工作线程、取消时异步断开连接、移除尚未开始的取消任务，并在读取过程中检查取消。调用方保留取消异常，并在解析及缓存前再次检查状态。保留 HTTPS、不跟随重定向、4 MB 响应上限及翻译最长 60 秒的单次读取超时；另设覆盖排队和整次读取的总超时。
2. **429 限流会错误拦住有效缓存。** 原逻辑先检查主机冷却时间，再读缓存，导致不需要联网的数据也无法使用。调整为先读有效公共缓存，冷却仅限制新的网络请求。显式刷新仍遵守限流，带凭证的请求仍不使用公共缓存。`Retry-After` 同时支持秒数与 HTTP 日期。
3. **LRCLIB 候选提示重复保留完整歌词响应。** 原 `known` 映射只用于提示文案，却持有数百份完整 `JSONObject`，与磁盘缓存重复；直接读取记录时还不会触发原搜索路径的数量清理。改为只保存计算后的提示字符串，统一使用最多 600 项的线程安全 LRU。原文、罗马音、无同步时间及纯音乐的提示规则保持一致，完整歌词继续按原路径读取和缓存。

## 边界

上述模拟器检查阶段未安装到真机；后续真机补测见下文。内存优化结论来自消除重复完整响应引用，不能据此给出固定 MB 或续航改善百分比。取消会立即释放协程等待者；个别厂商的底层 DNS／socket 如果忽略断开与中断，工作线程仍可能等待底层超时，迟到结果不会被采用。第三方服务可用性不能由受控测试保证。
