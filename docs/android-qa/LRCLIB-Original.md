## 根因

1. 原匹配规则按标题归一化后的全文比较，`movie ver.` 与 `Movie Version` 不相等，因此把正确日文稿排除了。
2. 带版本限定的结构化检索容易只找到精确命名的罗马音稿；取得一个可接受候选后就停止进一步发现。
3. 上一次提供方版本已经是 2，缓存仍可以长期复用，不会再触发此前只针对更旧版本的原文重选。

问题发生在检索、录音身份判断和缓存选择，截图案例不是显示组件把已有的日文换成了 romanization 字段。

## 实现

- `SongSearch.recordingTitle` 统一已知版本限定中的 ver./version 写法，继续保留 movie、original、English、Live 等录音差异；原始曲名仍用于显示，不伪改 API 元数据。
- `discoveryTitle` 仅为检索去掉尾部明确的版本后缀。带此类后缀的 LRCLIB 查找先用基本歌名＋歌手发现候选，再用完整版本、歌手及 5 秒时长边界验收，不把搜索范围放宽等同于自动绑定条件放宽。
- 非版本限定的精确匹配若只有拉丁字母歌词，再进行最多一次较宽检索，额外协程预算 4.5 秒。复用搜索响应中的歌词，避免无意义的 `/get`；取消、503 退避、缓存逻辑继续有效。可选发现失败时保留已成功取得的响应，不因额外查询导致原有可用结果丢失。
- 同一可靠录音内，日文同步原文优先，其次无时间轴日文原文；匹配窗口把可靠原文候选排在前面，同时保留其他候选供人工核对。
- 显式英语版本不因存在日文记录而替换为日文。英文同步字段也不会被日文普通字段覆盖。
- 两字段均没有原文时不将罗马音逆向猜成汉字/假名。普通原文缺少时间轴时静态显示，不把它与罗马音逐行硬拼。
- LRCLIB providerRevision 升至 3。现有 `AppGraph` 升级路径会重选旧拉丁字母缓存并更新绑定；无需清空整个歌词库。改变了原文或时间的行不沿用旧译文，未改变的行继续保留译文及来源。

## 范围与限制

该策略只在服务返回了可靠的原文候选时使用原文；没有原文、跨文字歌名没有可信别名、服务失败或版本无法确认时，不能凭空恢复原文。明确的相同版本写法已兼容，但未开放仅靠模糊歌名/相近时长覆盖所有不同录音。手动指定记录 ID 仍尊重用户选择；可在匹配窗口看到原文/罗马音候选提示。社区投稿的时间戳或内容本身仍可能有误，可使用现有校准或换源。
