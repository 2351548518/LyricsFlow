# 大备份同步编解码优化与复测

日期：2026-11-04。根据[首次测量](./Backup-Codec-Benchmark.md)实施优化：GitHub 同步直接校验 JSON 文件，ZIP 仅用于导出和恢复文件。界面、数据格式、合并规则与权限处理保持原有行为。

## 代码调整

- `Transfer.backupFiles` 直接生成原有三个 JSON 文件，上传预览不再生成 ZIP 再解开。
- `Transfer.validateBackupFiles` 为 ZIP 导入和 GitHub 文件提供同一套完整内容校验。上传预览仅解析一次并生成摘要；网络等待及确认期间只保存文件和摘要，不持有这次解析的记录。
- `SnapshotFiles.readArchive` 单次限量解压，`unzip` 校验这一次解出的内容，不再第二次解压。按剩余解压总量限制读取，避免到最后一个文件才发现累积超限。
- GitHub 下载只校验一次，待确认下载保留解析结果，摘要与恢复复用；普通连接、上传检查与恢复前云端版本复核均不长期保留解析记录。取消预览时一起释放。
- 上传是独立边界，仍对实际传入文件重新做完整校验，防止预览后可变映射的内容改变而绕过检查，但不经过 ZIP。恢复前继续复核云端 head 并以 AtomicFile 保存原资料的 ZIP；仓库隐私和非强制更新规则不变。
- 旧 ZIP 缺少可选 settings.json 时仍可导入；GitHub 快照仍要求三个完整文件。未知/重复路径、20 MB 总量、3000 条记录、主题/歌词/逐曲选择/图片等原有内容检查继续有效。

## 同轮对照测量

HONOR MLY-AN00、API 37、独立 `.qa` Debug 包、384 MiB 最大 Java 堆。固定随机种子、记录数、原始字节和 ZIP 大小均与首次测量一致；每项预热一次后测 5 次，轮换顺序，共 90 条样本。不访问正式应用数据或网络。

这轮增加 `legacy_preview_control`：在相同构建内保留旧链路的两次压缩、三次解压、两次完整校验操作，交替与新路径对照。该对照使用当前共享校验器，适合比较重复工作；不是历史旧二进制。新链路直接校验已准备好的三个文件，只解析一次。两种路径都以记录数消费结果并返回文件映射，排除数据库读取/JSON 组装与网络传输。

## 与历史基线的区别

| 数据量 | 首次旧版基线 | 本轮旧链路对照 | 本轮新路径 | 新路径 5 次范围 |
| --- | --- | --- | --- | --- |
| 0.52 MB | 316.55 ms | 168.56 ms | 65.97 ms | 63.38–67.64 ms |
| 5.01 MB | 2657.13 ms | 1451.91 ms | 547.45 ms | 529.34–550.15 ms |
| 15.02 MB | 8266.12 ms | 4365.78 ms | 1605.68 ms | 1573.36–1631.49 ms |

首次 15 MB 旧基线范围约 5.04–8.53 秒，存在明显波动。本轮开始/结束 Thermal Status 为 0/1；温控、ART 和调度仍可能影响时延，因此主要使用同轮轮换对照，不能把跨轮历史差值全部归因于改动。

5 ms 间隔采样的是已用 Java 堆，可能漏掉短峰；累计分配包含已回收临时对象。Debug 仪器测量不是 Release 绝对性能，数据不含图片，不代表所有真实备份，也未测电池耗电。下载解析结果的复用和生命周期调整通过代码及功能测试验证，没有独立量化其长期内存收益。最后的生命周期微调不改变本基准调用的编解码函数。
